## 1 当前能开始到什么程度

仓库已有 Core 只读状态/生命/构筑/姿态、伤害/交互/卡片端口与 Audio Core 空后端。本轮新增 IPlayerInput 和 C01 运行/输入/启动源码，Unity 编译已通过；`Assets/Scenes/Tests/C01/C01_Smoke.unity` 已接线/保存/重载，实际 Play 的 32 项自动检查通过，Inspector 倍率验证及重复入口/缺引用检查通过；最终结果尚待发布新提交。真实玩家状态、运动、攻击、交互选择器与结算服务仍未实现。SampleScene 不是交付地图；地图作者以独立场景交付，实际路径尚待登记。

可以立即开展标为“可独测”的任务，用既有接口的局部测试替身验收。它们可以在正式底层完成前交付，但必须区分“测试场景通过”和“主场景集成通过”。不能把测试替身当作另一套正式状态系统带进主场景。

移动、攻击、奖励和传送按各自依赖逐项放行，不要求先把整个游戏底层一次完成。数值未冻结可使用标明的 Inspector 暂定值；扣费、下限、暂停等语义问题仍须总控明确。

## 3 任务总览

### 阶段与放行标准

第一阶段是技术与操作的最小落地：先验收个人任务，再由总控把已通过功能接在同一份短灰盒中。它不等于已经完成正式奖励/代价结算或整局游戏。

| 阶段 | 本阶段交付 | 分工时机 |
|---|---|---|
| 第一阶段：最小落地 | C00、C01/C02/C03 的当期最小接口；T01 菜单、T02 HUD、T03 开关门、T06 跑跳、T07 咬击靶子；每项独测并完成下表的总控集成验收 | 现在按依赖领取，成员与文件范围由总控登记；T04 相机、T05 单音效可有余力时并行 |
| 第二阶段：核心玩法闭环 | 在第一阶段真实底层上接获得→保留/替换→舍弃/负面→付费传送/回溯；逐步接首版能力 | 第一阶段验收通过后，根据代码实际状态、成员人数和未决规则重新分配 |
| 后续阶段：整局与交付 | 三层地图、战斗/危险/终点、音频完整性及 Windows 整局验证 | 核心闭环可玩后再拆任务、分人和冻结范围 |

T08–T18 是后续候选任务卡，便于提前看见依赖，不是已经开工的排班表。以后可依实际实现合并/拆分；本轮不分配后续人员、不要求同时开始。第一阶段 T04/T05 若未完成，登记后续待办，不因此阻止程序灰盒通过；它们进入最终版本仍须按本卡验收。

### 第一阶段每个领取者的验收

成员领取某个 ID 时，该行及对应详细任务卡就是其验收标准；不是只说“负责 UI”或“负责玩家”。同一人领取多项时逐项验收，不能以其中一项通过代替其他项。

| 领取任务 | 必须当场复现 | 交给总控的材料 |
|---|---|---|
| T01 菜单 | 三项确认/取消、同事务切四项、false 不关闭、连点不重复 | 菜单 Prefab、独立场景、测试回调入口与真实请求接入说明 |
| T02 HUD | 真实/测试生命事件刷新、四项槽位、姿态与不可用剑；启停不残留监听 | HUD Prefab、图标/字段配置、绑定的接口与组件说明 |
| T03 开关门 | 触发一次开门且可通行；重复不重播；缺引用可定位 | 开关/门 Prefab、引用关系、独测场景 |
| T06 跑跳 | 正式输入控制跑跳/落地/碰墙；暂停锁有效；Inspector 调参生效 | 运动组件、配置、测试玩家；地面层、尺寸、输入接点与平台试走结果 |
| T07 咬击 | 正式输入命中靶子、实际扣血；多 Collider 不重复；站立/暂停/死亡禁止咬击 | 攻击组件/配置、测试靶子、伤害链说明与复现步骤 |
| T04 相机（可选并行） | 跟随、边界/偏移可调、目标丢失处理、瞬移跟随 | 相机组件与测试场景，不新增重复相机/Listener |
| T05 音频（素材具备时） | 指定 Cue 实际播放、缺 Bank 不影响运行、卸载正常 | 后端/映射、所需 Bank/meta、相对路径与另一份 checkout 的结果 |

每项都必须附个人 handoff 与代码标注，注明真正做过的验证。只有脚本/日志或仅编译通过，不能代替要求操作的 Unity Play 结果；尚不能启动 Unity 时可交“待验收”，由有环境的成员执行操作后记录实际结果。

### 第一阶段总控整体验收

总控承担的是接入后可运行的结果；共享实现可委托，验收归总控。使用短灰盒或地图作者交付的短区段，不等待完整三层地图。

1. 从本阶段已发布提交取得项目，Unity 6000.2.9f1 可导入/编译，明确唯一入口场景及启动步骤。
2. 入口中只有一套真实玩家状态、输入和运行阶段；正式玩家通过输入跑跳、碰撞平台，咬击经真实伤害入口使靶子扣血。
3. 玩家用正式交互输入打开一扇门；已开状态在同局保留。交互器只按本阶段已发布规则处理，不默默确定尚未批准的并列对象策略。
4. HUD 接入真实状态，实际生命变化可见；初始空构筑/四足显示正确。构筑/姿态变更本阶段可在独测场景验证，不假装已完成奖励服务。
5. T01 在独立菜单场景通过三项/四项事务生命周期验收；若已接入灰盒，其入口明确标“测试菜单”，无真实领奖/收费声明。正式结算由第二阶段接入。
6. 代表性 Inspector 参数改变后实际生效，配置与引用已保存；暂停/恢复不残留动作输入；离开/重进测试无重复对象或事件。
7. 总控导出 Windows 灰盒，至少在开发机脱离编辑器启动并复现移动/交互；另一台电脑测试在可用时记录，其缺失不得写成通过。最终交付仍要求另一台 Windows 机器验证。
8. 记录各任务验收结果、基线提交、已集成列表和已知问题；阻塞操作/状态正确性的问题修复后重验。可选音频/美术缺口有明确后续记录。

以上要求全部满足才标“第一阶段通过”。个人“独测通过”不能代替此结论。C00 编辑器检查与 C01 独测已完成；其余任务与第一阶段整体验收仍未执行，不能把 C01 通过写成第一阶段通过。

### 第一阶段怎样按最小批次合入并验证

**第一阶段必需队友任务是 T01、T02、T03、T06、T07，不是按编号连续做到 T07。** T04 相机和 T05 音频可独立合入，不阻塞最小程序灰盒；T08–T18 是后续候选。队友任务总计 18 项，不代表 18 个人或 18 个固定岗位；其他程序仍为人数未定、不超过 5 人，默认一人同时一个开发中任务。

| 合入批次 | 所需任务与依赖 | 这一批必须可以实际测试 |
|---|---|---|
| 底层基线 | 总控 C00＋C01 | Unity 编译、独立场景启动、真实输入缓冲/阶段锁、退出清理；发布明确提交号 |
| 跑跳 | T06，基于已发布 C01 | 正式输入移动/单跳、落地/墙体、暂停恢复；运动参数和地面层可调 |
| 状态与战斗 | 总控 C02 → T02、T07 各自独测后分别合入 | 唯一生命/构筑/姿态状态，HUD 同步；正式 Attack 咬击靶子实际扣血 |
| 正式交互 | 总控 C03 → T03 | 正式 Interact 按已发布选择规则开门，重复不重播，同局保持 |
| 菜单接线 | T01（可更早独测/合入），需要 C01/C03 才接灰盒入口 | 三项确认/取消、四项替换、false 不关闭、重复提交保护；灰盒入口标明测试事务 |
| 第一阶段发布 | 总控串行集成以上结果并导出 Windows 灰盒 | 完成上节全部集成验收；脱离编辑器复现跑跳/交互，记录未测的外部机器 |

表格是依赖与可测结果，不要求多人等上一行全部完成才开工。T01/T02/T03 可先用任务内替身独测；C02/C03 可按所需接口逐项发布。合入 C02 后 T02/T07 才用真实状态接入；不能把测试替身当正式状态。

每个最小合入单位交付自己的源码、配置/Prefab、独立场景/meta、handoff。总控先在独立场景按任务卡验收，再一次合入一个已通过任务到 Ming，显式接线并复测此前闭环；不要同时切分支/merge 或把未验收的大功能混在一起。本规则不授权 Codex 自动 commit、merge 或 push。

第一阶段完成后，第二阶段优先接 T12 宝箱与 T13 付费传送，再按冻结规则接能力；并不是第一阶段就要一次做完 T01–T18。T04/T05 的缺口仍需登记，最终版本必须补齐相应验收。

### 第一阶段通过后的下一次派发

总控先查看真实提交、各人的 handoff 与已知问题，再按当时人数选择第二阶段的最小闭环任务。优先补齐会影响奖励/付费规则的决定，然后拆真实事务、宝箱、传送及其测试；复用已验收面板与状态。重新确认每项输入/输出、可写文件、验收和集成顺序，避免把本文的候选顺序当作过时的强制排班。

## 4 统一交付与文件定位

每张任务卡交付本功能源码、需要的配置与 Prefab、一个可独立操作的测试场景、对应 meta、个人 handoff 和几步可复现的验收。输入/状态依赖未完成时，测试驱动仅存在于任务的测试范围，复用已有接口；测试场景不进入正式构建，正式入口不引用替身。

建议测试场景统一为 `Assets/Scenes/Tests/Txx/Txx_Smoke.unity`；测试辅助代码为 `Assets/Scripts/Tests/Txx/`；配置为 `Assets/Configs/<功能名>/`；Prefab 为 `Assets/Prefabs/<功能名>/`。正式源码在下面任务卡标明的目录内自主拆分。所有路径是任务范围建议，领取时由总控记录实际范围，不强制类名。

除非任务明确委托，否则不修改 Core、Audio/Core、主场景、共享玩家 Prefab、公共输入、Packages 或 ProjectSettings。测试需要角色时用本任务的实例或 Variant，最终共享玩家由总控组装。若两个任务需要改同一个运动脚本/配置/Prefab，先集成前一个任务，再串行修改，不能仅凭不同任务编号判断无冲突。

## 5 第一批可独测任务卡

## 6 底层发布后领取的任务卡

## 7 人数变化时怎样领取

总控持续推进 C00–C05；其他人从依赖已满足的任务中领取，每人默认同时一个开发中任务，交付可测结果后再拿下一个。人数少时顺序串联，人数增加时填入互不改同一文件的任务，不拆出五套管理器。

第一批可选 T01/T02/T03/T04；音频素材具备时 T05 可独立推进。第五位程序若不是音频维护者，可以接总控明确委托的 C01 或 C02 子任务；若缺少可独立验收的工作，就协助跑已交付任务的验收，不为凑人数改同一个核心文件。

T06 依赖发布后优先开工。T07→T08 适合连续领取；T10/T11 若共享运动文件则串行；T12/T13 若共享结算服务则总控先发布该服务或串行委托，不能把同一共享服务分给两人。T17 在 T13 的全负面池集成之前完成。

任务状态由总控登记为：未领取 → 开发中 → 待验收 → 独测通过 → 已集成；阻塞时记录具体依赖，不等同完成。成员只更新自己的 handoff，避免多人同时编辑此任务目录。开始任务前通过总控确认领取，文件里写上名字本身不构成锁。

## 8 地图正在制作时的配合

保持当前地图作者的文件维护权。交付方式已确认是独立地图场景，先登记实际 .unity 路径及其依赖；总控在该场景接入运行组件，继续按单游戏场景运行，不要求改成 Prefab 或引入叠加场景加载。程序测试仍在各自场景进行。

地图作者制作时总控不同时写该场景；交付后总控接线，后续改图再协调交还编辑权。提前验证可使用一次性的测试副本，不维护第二份长期主地图。交付场景保存到 Git 时需包含所引用的 Tilemap/Sprite/材质/Prefab 及 meta，不能只交 .unity 文件。

总控与地图作者只需先对齐这些接点：

| 接点 | 地图交付信息 | 程序接入 |
|---|---|---|
| 出生点 | 安全位置与朝向 | 唯一玩家实例由总控放置 |
| 地面与阻挡 | Collider2D、可行走区域、场景尺度 | 总控统一 Layer；T06 验证角色尺寸和基础跳跃 |
| 传送入口/落点 | 位置、目的地对应关系、安全空间 | T13 Prefab 通过引用接线，不根据对象名搜索 |
| 开关/门 | 位置与实际控制关系 | T03 接线；涉及主线锁门规则先确认 |
| 宝箱/敌人/陷阱 | 摆放位置或临时标记 | 接入已验收 Prefab；地图作者不另写状态/伤害逻辑 |
| 精英/出口 | 第三层位置和通道 | T15 接入唯一胜利条件 |
| 相机边界 | 地图可见范围与分层边界 | T04 参数绑定 |

地图作者可以继续布局和美术。未确认的每层两箱、层间连接、机关控制关系仍是提案；总控收集地图现状再核对，不为追赶旧提案擅自重做地图。先拿一个短区段与 T06 试走，确认基础移动尺度后再铺满。
